### **Решение**

#### Ключевые проблемы текущего состояния

1. **`BookingService` зависит от всех остальных модулей.** При создании бронирования `BookingService` синхронно вызывает `AppUserService`, `HotelService`, `PromoCodeService` и `ReviewService`. Сбой или замедление любого из них блокирует создание бронирования.

2. **Одна база данных.** Все пять таблиц находятся в одной схеме PostgreSQL.

3. **Смешение чтения и записи.** Запись бронирований и чтение каталога отелей обрабатываются одним процессом.

4. **Расчёт надёжности.** При каждом `POST /api/bookings` система агрегирует все отзывы отеля для проверки средний рейтинг >= 4.0 и количество >= 10. Это запрос O(N) по количеству отзывов на каждую операцию записи.

5. **Дублирование VIP-логики.** `AppUserService` и `PromoCodeService` читают VIP-статус пользователя. Изменение правил VIP требует правки в двух местах.

6. **Отсутствие версионирования API и BFF.** REST API монолита обслуживает все клиентские платформы одинаково. Адаптации под конкретную платформу нет.

#### Почему первым выносим Booking

- Бронирование создаёт основную write-нагрузку и является бизнес-критичной операцией. Масштабировать нужно именно этот модуль.
- `BookingService` зависит от всех остальных модулей. Его вынос сразу разрывает центральный узел зависимостей.

#### План миграции по Strangler Fig

1. Развернуть `booking-service` с собственной базой данных PostgreSQL. API сервиса работает по gRPC в соответствии с готовыми протобафами.

2. Включить прокси в монолите. REST-контракт `/api/bookings` для внешних клиентов не должен менятся.

3. На переходный период `booking-service` валидирует пользователя, отель, промокод и отзывы через синхронные REST-вызовы в монолит. Монолит выступает источником данных для этих проверок.

4. Перенести данные таблицы `booking` в новую базу данных. На переходном периоде писать в две БД.

5. Публиковать событие `booking.created` в Kafka. Подписчики получают уведомления о новых бронированиях без синхронных вызовов.

6. Поведение API должно остаться идентичным.

### **Альтернативы**

1. **Начать с листового сервиса: `HotelService` или `ReviewService`.** Риск выноса ниже, так как у этих модулей нет входящих зависимостей от других сервисов. Однако это не решает главную проблему масштабирования записи бронирований и не разрывает центральный узел зависимостей.

2. **Переписать всё сразу.** Полная миграция за одну итерацию. Команда из двух разработчиков и архитектора не может параллельно поддерживать монолит и строить все микросервисы. Риск срыва сроков и потери стабильности высок.

3. **Модульный монолит: разделить код на Gradle-модули без отдельного деплоя.** Улучшает структуру кода и изоляцию зависимостей на уровне сборки. Не даёт независимого масштабирования и отдельных релизов.

4. **REST вместо gRPC между монолитом и `booking-service`.** Проще отлаживать, стандартные инструменты мониторинга. Однако прокси-слой в монолите уже реализован под gRPC. Бинарный протокол даёт меньший объём трафика на межсервисных вызовах.

### **Недостатки, ограничения, риски**

1. **Сетевые сбои между монолитом и `booking-service`.** Появляется распределённость: сетевой вызов вместо локального метода. Необходимы таймауты и повторные попытки.

2. **Обратная связность на переходном этапе.** `booking-service` вызывает монолит по REST для валидации пользователя, отеля, промокода и отзывов. Временная циклическая зависимость: монолит проксирует в `booking-service`, а `booking-service` обращается обратно в монолит.

3. **Рассинхронизация данных при переносе таблицы `booking`.** На этапе миграции данных в отдельную базу возможна потеря или дублирование записей.

4. **Рост операционной нагрузки.** Два сервиса вместо одного - увеличивается нагрузка на одного DevOps-инженера.

5. **Увеличение латентности `POST /api/bookings`.** Добавляется один сетевой переход: монолит отправляет gRPC-запрос в `booking-service`. Обратные REST-вызовы в монолит добавляют ещё по одному переходу на каждую валидацию.
